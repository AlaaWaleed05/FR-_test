# Component: printed-form PDF rendering (backend)

Toolchain: **Apache FOP 2.11** (`org.apache.xmlgraphics:fop-core`), XSL-FO → PDF. Apache-2.0.
Decided 2026-09-13 as **AD-014**, wayfinder ticket 03. Alternatives and why they lost:
`docs/sessions/2026-09-13-research-arabic-pdf-toolchain.md`.

**Accepted live at S8-33 (2026-09-14).** The research's section 8 made the recommendation
conditional on a render being produced and read by someone who reads Arabic, because if FOP
mis-shaped the face the layout would be thrown away with the library — XSL-FO does not port to
HTML. That render exists: `FopArabicAcceptanceRenderTest` writes the PDF, a PNG of each page, the
extracted text and FOP's own event log to `backend/target/acceptance-render/`. It was read.
**FOP passed.** AD-014 is no longer conditional.

## What the acceptance render proved

- All four Arabic positional forms join; the **lam-alef renders as one ligature**; no word broke.
- The content stream carries **Arabic-block codepoints (U+0600..U+06FF), never presentation forms**
  — so FOP applies the font's GSUB tables rather than pre-shaping to U+FE70. That is a real
  observation rather than a default: this font DOES carry 140 presentation-form `cmap` entries
  (measured with `fontTools`), so the legacy path was available and FOP declined it. It also
  answers the research's one open font question.
- A synthetic account number, an E.164 number and a `FRU-` reference keep their **digits in logical
  order** inside an RTL paragraph.
- `writing-mode="rl-tb"` puts labels on the right; `fo:page-number` +
  `fo:page-number-citation-last` resolve "page N of M" across a forced three-page document.
- The **only** missing glyphs in the whole document are U+2068/U+2069, fed to it deliberately.

## Rules, each one load-bearing

- **Complex scripts are ON by default. Never pass `-nocs` / `setComplexScriptFeatures(false)`, and
  never add `<complex-scripts disabled="true"/>` to `fop.xconf`.** Turning it off is how a connected
  script silently renders as disconnected isolated letters, with no error of any kind.
  [DOC `fop/2.11/complexscripts.html`]
- **Embed the `.ttf`, never an `.otf`.** FOP extracts CFF data from an OpenType/CFF font and
  re-embeds it as Type1C, losing the layout features that join the script. Plain TrueType keeps
  them. [DOC `fop/2.11/fonts.html`]
- **Font: IBM Plex Sans Arabic Regular + SemiBold**, full upstream TTF, at
  `backend/src/main/resources/fonts/`, generated by `mobile/tool/fetch_and_subset_fonts.py`. The
  backend does not read across into `mobile/`, and FOP subsets on embed anyway, so the full face
  costs nothing in the output. OFL 1.1 permits embedding and does not license the document
  [DOC `openfontlicense.org/ofl-faq` 1.12/1.13].
- **Font: Amiri Regular**, same source and same rules, bundled since S9-06. Ticket 08 decision 2
  still sets the whole form in Plex; Amiri answers for ONE span, the app name «بياناتي» in the
  header, set as the mobile splash sets it — AD-022 (i). **It is registered at normal/normal ONLY,
  because the generator bundles Regular alone** (a bold Naskh at display size reads as heavy rather
  than emphatic). That makes the 700 hazard below live for this face in a way it is not for Plex:
  there is no heavier Amiri to answer a bold value, so the span pins `font-weight="normal"` rather
  than inheriting. Registering a 700 triplet for Amiri would point at a face that does not exist.
- **Register weight 700, not only 600.** Found live at the acceptance render: XSL-FO's
  `font-weight="bold"` resolves to the numeric weight **700**, so a face registered only at 600 is
  not a match. FOP then substitutes `any,normal,700`, which resolved to the built-in Times-Bold —
  and Times has no Arabic, so every bold Arabic word on the page became a missing-glyph box while
  the document still rendered and still paginated. Plex ships no 700 weight, so SemiBold answers for
  both 600 and 700.
- **`classpath:` needs a resolver; FOP has none.** `FopFactoryProvider` exists for this. FOP
  resolves `embed-url` through xmlgraphics-commons' default resolver, which is built on
  `java.net.URL`, and `classpath:` is a Spring scheme rather than a JDK one. **A font that will not
  resolve does not fail the render** — FOP reports a "Font not found, substituting" event and
  carries on with Times. Using a file path instead would work on a developer machine and fail in the
  deployed image, where the fonts live inside the Boot fat jar.
- **Page direction: `writing-mode="rl-tb"`.** The properties `direction` and `unicode-bidi` are NOT
  implemented by FOP as properties; direction is expressed by `writing-mode`, by `fo:bidi-override`
  and by control characters. [DOC `compliance.html`]

## Mixed direction — the rule that the research got wrong

Every line on this form pairs an Arabic label with a Latin value: an account number, a `+249` E.164
phone number, a `SFB-`/`FRU-` reference, a date, a Latin name off the MRZ.

**Wrap every such value in `<fo:bidi-override direction="ltr" unicode-bidi="embed">`.**

This CORRECTS section 6 of the research and the card draft in its section 10, both of which said to
give the value its own `fo:block` with `writing-mode="lr-tb"` and insert no control characters, on
the reasoning that a block is its own bidi paragraph. Rendered and read at S8-33, that leaves
`+249912345678` displayed as `249912345678+`, the leading `+` dragged to the far end — exactly the
defect wayfinder ticket 08 predicted would "bite again in the PRINT renderer". It is not a FOP bug:
a leading `+` is bidi class ES, it is not between two numbers, so UAX#9 resolves it as a neutral and
a neutral beside Arabic text takes the paragraph direction.

Five spellings were rendered side by side (acceptance render, page 3). Bare and own-block-`lr-tb`
are wrong; `bidi-override`, `embed`, and `embed` around a Latin name are right.

**Use `embed`, not `bidi-override`.** `bidi-override` forces every character in the run to LTR
whatever it is, so an Arabic word that ever reached a field tagged as a Latin value would render
reversed letter by letter and still look like text. `embed` opens an LTR embedding and lets UAX#9
resolve the inside, so the same field degrades to correct rather than to plausible nonsense. Every
value on this form comes from a customer or a scan, so degrading safely is the requirement.

Both are MARKUP: unlike the LRM/RLM and LRE..PDF alternatives, they insert nothing into the string
an operator can select and copy out of the PDF, and they raise no missing-glyph event.

## Do NOT use FSI/PDI here

`mobile/lib/core/text/ltr_value.dart` has an `isolate` helper built on U+2068/U+2069. **It must not
be copied into this renderer.** FOP's `BidiConstants` defines nineteen bidi classes and none of them
is an isolate — its implementation predates Unicode 6.3. Predicted from source by the research
(R-5), and confirmed live at the acceptance render: the two characters had **no isolating effect
whatsoever** (the line renders identically to the same line without them) and each raised a
missing-glyph event. They were dropped rather than drawn as boxes on this font, which makes the
failure silent rather than visible — the worse of the two outcomes. The renderer carries this as a
comment, not only here.

## Mechanics

- `FopFactory` is a **thread-safe singleton**; building one parses and caches font metrics for every
  embedded face. A `Fop` instance is the per-document object. [DOC]
- **The FO document is GENERATED WITH ESCAPING, never string-concatenated**, and the
  `TransformerFactory` is configured for secure processing with external entities disabled. Every
  field on this form is customer- or scan-supplied, so a name containing `<` or `&` breaks the
  document and a crafted one could inject markup (research R-2). Both are implemented:
  `FoDocumentWriter` writes through `XMLStreamWriter` and `PrintedFormRenderer` sets
  `FEATURE_SECURE_PROCESSING` with empty external-DTD and external-stylesheet properties. The
  ACCEPTANCE RENDER is the exception and says so at its own `acceptanceFo()`: it interpolates
  strings, which is safe only because every value in it is a literal in the test file.
- **Render once, into a `byte[]`.** The same bytes are streamed to the operator and stored
  (ticket 05 decision 4). A stored print can never be re-derived and compared — FOP stamps a
  creation date and a document id, so the render is not byte-reproducible and the stored checksum
  is the only proof of what was printed.
- Paper is **A4** (ticket 08 decision 5).
- **PDF/A is not requested.** Product-owner ruling 2026-09-14 (S8-33): plain PDF now, and archival
  conformance goes to the bank as a separate question. Turning it on changes font-embedding rules —
  full embedding, no subsetting — so it is a deliberate decision, and `fop.xconf` is where it would
  be taken.

## The attachment bundle, and why PDFBox is a main-scope dependency

Product-owner ruling, 2026-09-14. The operator is asked ONCE at print time whether to print the
attachments. If yes, the five images print again full size, one per page after the form, and the
salary certificate follows on its own page. One document, not two files — the product owner was
explicit that a printed certificate is a separate *paper*, not a separate *file*.

**FOP cannot lay out an existing PDF page.** The certificate is the one artifact that may be
`application/pdf` — the only kind whose content-type allow-list admits one — so the finished
document is assembled in two steps: FOP renders the form and the image attachments, then PDFBox
appends the certificate's pages. That is why `pdfbox` moved from test scope to main scope, and it
reverses wayfinder ticket 05 decision 9's reason for avoiding it ("merging would have meant adding
PDFBox purely to staple a customer's file onto the bank's"), which rested on the certificate being
a separate document.

The certificate's pages are **copied, not re-rendered**, so the operator holds the customer's own
document. The stored artifact is untouched and its checksum still describes the uploaded bytes.

Two limits worth knowing before they are rediscovered:

- **The footer's page count covers the bank's pages only.** «صفحة N من M» is resolved by FOP over
  what FOP laid out, so a six-page form-plus-attachments prints "6" while the file has seven sheets.
  Making them agree means computing the total before the render and giving up
  `fo:page-number-citation-last`.
- **An absent image gets no attachment page.** The form's own images section still shows «غير متاح»
  for it. A profile whose uploads never landed has no artifacts at all, so the alternative would
  be a handful of blank sheets. (This read "a manually completed profile" until AD-022 removed
  that journey on 2026-09-16; the rule and its reason are unchanged.)

## Reading the form back is not a test oracle

Two things render correctly and cannot be asserted from extracted PDF text, both found the hard way:

- **Arabic diacritics reorder.** A string carrying damma, fatha and shadda — «لا تُسلَّم للعميل», the
  internal-use notice this form printed until S9-06 — comes back with the marks interleaved, because
  FOP positions them with GPOS. Kept as the example after the string left the form: the behaviour is
  FOP's, not that notice's.
- **Some shaped glyphs extract as private-use codepoints.** «الفرع» comes back containing U+E000 and
  U+E001, because the embedded subset's ToUnicode CMap has no reverse mapping for those forms.
  **Amiri is worse: the whole word goes.** «بياناتي» in the header extracts as ten private-use
  codepoints, U+E000..U+E006 and nothing else — measured at S9-06. It renders perfectly. The
  consequence is that no assertion on extracted text can prove the header is present, which is why
  the per-page header guard in `PrintedFormRendererTest` asserts on what the page DRAWS instead.

Assert such things on the FO, where order and markup are exact, and confirm the visual by reading
the rendered PNG. Bidi reordering is a third case: PDFBox puts a trailing tag *before* its value
when extracting an RTL line, which silently defeated one assertion in this session.

## Dependency notes

`fop-core` excludes `xml-apis:xml-apis` and `xml-apis:xml-apis-ext`, which arrive via Batik and put
a 2009 copy of `org.w3c.dom`/`org.xml.sax` on the classpath, shadowing the platform's `java.xml`.
Research R-6 also predicted a `commons-logging` collision with `poi-ooxml`; measured both ways, there
is none — Spring Boot's BOM pins it. The reasoning is recorded in `backend/pom.xml` beside the
dependency.

Batik arrives with FOP and carries its own CVE history (R-4). The renderer processes only FO it
generates itself, never an uploaded document, and the form's logo is a PNG rather than an SVG, so
nothing we author reaches Batik.
