## 8. `@agent-reviewer` — two passes, full disposition

**First pass**, 2 SHOULD-FIX + 2 NOTE, all fixed:

| Finding | Fix |
|---|---|
| `ReferenceDocumentPublisher#publish` was `@Transactional`, but every call path is self-invocation (`publishAllCurrentVersions` calling `this.publish`) or a direct `new` in the test — the Spring AOP proxy never applies, so the annotation was a no-op. A crash between the document upsert and the `content_hash` update could leave them permanently out of sync. | Replaced with an explicit `TransactionTemplate` (constructor now takes `PlatformTransactionManager`); the integration test builds a `DataSourceTransactionManager` over the same `DataSource` its manual `JdbcTemplate` uses so the boundary is real in the test too. |
| V0049's constraint trigger covered only `ref.reference_item` writes. A later `UPDATE` touching only `ref.reference_list_version.root_item_code` (e.g. a future correction migration) had nothing catching a wrong value — the composite FK alone only proves the new value is *some* published country code, not that it matches this list's own parentless row. | Added a second constraint trigger, `reference_list_version_root_check`, `AFTER UPDATE OF root_item_code, root_country_version`, reusing `ref.trg_assert_list_root()` (its `NEW.list_code`/`NEW.version` resolve correctly against either table). |
| R-033 was marked ✅ Retired on the strength of a mechanism (`content_hash` = hash-of-bytes) that only takes effect once the by-hand publication step actually runs — an R-028-shaped skip risk (Layer 3's own script has the identical weakness). | Downgraded to 🟡 Watching in RISKS.md and persistence.md, wording stating plainly what's structurally fixed (the definition) versus what's still operational (population). |
| `ReferenceListDocumentInput.itemCount`'s Javadoc claimed it "can be compared" against the real row count; nothing did. | Added the check to `ReferenceDocumentPublisher#publish`, throwing `IllegalStateException` before any write. |

**Second pass, against the fixed diff, found the first pass's own fixes had no regression
tests** — this project's tenth consecutive session where the re-review finds a defect in, or an
unproven gap around, the first pass's own fixes:

| Finding | Fix |
|---|---|
| Neither the `TransactionTemplate` fix nor the `itemCount` check had a test that would fail if reverted — "a green test could coexist with a broken guard." | Two new integration tests: `aFailureInsideAnOuterTransactionRollsBackBothWritesTogether` (wraps `publish()` in an outer transaction that then throws, asserts neither write landed) and `itemCountMismatchIsRejectedBeforeAnyWrite`. |
| PROJECT_PLAN.md's AD-002f row still said "closing R-033" after RISKS.md/persistence.md had both been walked back to open. | Reworded to "redefines R-033's envelope but does not close it." |
| The test class's namespace-claim comment overclaimed: `s403_root_fk_test` lands in `ref.reference_list` only (its `reference_list_version` row is the one rejected under test), not both tables as originally written. | Corrected in both the test class's own Javadoc and `AbstractPostgresIntegrationTest`'s documented list. |
| `ref.assert_list_root` also reads `ref.reference_list.is_hierarchical`, and no trigger guards an `UPDATE` to *that* column — the same shape as the fixed gap, one table over. | Deliberately NOT built: no code path in this codebase's history ever updates `is_hierarchical` after a list's seed-time INSERT (unlike `root_item_code`, a real expected correction path once OQ-012 lands). Recorded as an explicit, documented scope boundary — V0049's closing comment and `docs/components/reference-data.md`'s Open section — rather than a third trigger against a write path nothing exercises. |
