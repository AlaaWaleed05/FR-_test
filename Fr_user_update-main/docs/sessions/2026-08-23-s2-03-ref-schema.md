## 3. The plan, and what changed after approval

Full plan: `C:\Users\DELL\.claude\plans\snug-doodling-ritchie.md`. Approved without
requested changes before implementation. Then `@agent-reviewer` was run against the diff
(§10 below) and found six real issues, all fixed before this report was finalized:

1. **Two real bugs, not judgment calls.** V0014 and V0016's `content_hash` canonicalisation
   used an *actual embedded newline* inside a `string_agg` separator argument
   (`E'` followed by a literal line break, then `'`) instead of the two-character escape
   `E'\n'` that V0015/V0017/V0018/V0019 correctly used. Root cause: a Python-generated
   f-string mis-escape in the two migrations that were generated programmatically rather
   than hand-typed. With `core.autocrlf=true` on this machine and no `.gitattributes` entry
   pinning `*.sql` to LF, a fresh Windows checkout would convert that literal newline to
   CRLF, changing the separator's bytes and making `content_hash` differ between a
   Windows-checkout run and a Linux run for byte-identical data — defeating the property
   AD-005 §9 relies on ("two publications with the same content produce the same hash").
   Fixed in both files; re-verified with a full rebuild (§6/§7 below reflect the fix).
2. **V0019 (rejection_reason) hardcoded `sort_ordinal` as REJ-code order**, reasoning it was
   an operator-facing list with no search picker. The task's general rule (§3, "computed at
   publication time... `row_number() OVER (ORDER BY label_ar COLLATE "ar-x-icu")`") states
   no exemption for this list — only `education_level` is explicitly carved out, by
   customer.md itself. This was scope I gave myself without a stated basis; corrected to the
   same window-function formula as every other list.
3. **Cross-list `content_hash` canonicalisation was inconsistent** — four different field
   sets and three different orderings across the six seed migrations (a genuine finding: I
   had not treated this as one contract). Unified to one format
   (`item_code|parent_code|label_ar|label_en`, empty string for an absent field) and one
   ordering (`item_code COLLATE "C"`) in all six files. Flagged explicitly in V0014's header
   comment as **not** a settled AD-002f wire format — only this session's internal
   self-verification — per CLAUDE.md's rule that open architecture decisions are not settled
   in passing. `reference_list_version` rows are never deleted, so a future AD-002f decision
   changing this format costs nothing already submitted.
4. **A real FK-bypass gap**: both closed FKs default to `MATCH SIMPLE`, under which a row
   with the code column set but its paired version column left `NULL` skips the FK check
   entirely (any NULL member column exempts a `MATCH SIMPLE` FK). `MATCH FULL` cannot be
   used instead, because `occupation_list`/`reason_list` are `GENERATED ALWAYS AS (constant)`
   columns that are never NULL. Closed with two additional `CHECK` constraints in V0013
   pairing each code column's nullability with its version column's — beyond the two literal
   `ALTER TABLE` statements S2-02 pre-wrote as comments, the same kind of judgment-call
   extension S2-02's own V0010 made to the `app` schema.
5. **No automated guard on the seeded row counts or the two FKs.** Added a second `@Test` to
   the existing `AppSchemaConnectivityIntegrationTest` (same migrated Testcontainers context,
   no extra container) asserting each list's row count and that both FK constraints exist —
   so a later edit that drops a row or a whole list fails the gate, not just this session's
   one-off proof.
6. **A citation error** in V0014's header comment: quoted the report as "...only the initial
   seed is a [migration]", eliding the word "repeatable" from the actual text ("only the
   initial seed is a repeatable migration") rather than addressing it. Corrected to quote
   accurately and explain the deliberate implementation choice: an ordinary versioned
   migration, not Flyway's `R__` repeatable mechanism, because `R__` re-runs on checksum
   change and would fail against the seed's own primary keys — "repeatable" in the report
   reads as "reproducible from the repository" (the same sense V0002's own comment uses),
   not literally `R__` syntax.

All six fixes are pure corrections to what this session already scoped — none required
touching anything from S2-01/S2-02, and none reopened a settled architecture decision.

## 5. The seed — migrations V0014–V0019

One migration per list, each self-contained: registers its `ref.reference_list` row,
computes `content_hash` + `item_count` from the same literal data it inserts (unified
canonicalisation per §3.3), computes `sort_ordinal` via
`row_number() OVER (ORDER BY label_ar COLLATE "ar-x-icu")` — except `education_level`,
which is explicitly ordinal per customer.md. Each combines its `reference_list_version`
insert and its `reference_item` insert into **one** SQL statement via a data-modifying CTE
(`ver AS (INSERT ... RETURNING ...)`), because PostgreSQL CTEs do not persist across
separate top-level statements in one migration script — found live on the first run
(`relation "ordered" does not exist`) and fixed before any other work.

- **V0014 occupation** — 135 rows from `docs/reference/كود_المهنة.xlsx` (138 `JOBCODE`
  rows read via openpyxl, codes 1–171 with gaps). **Deliberate deviation from AD-005 §9**,

  `is_active = false`, not omitted; this task's own instructions are explicit and more
  specific — "the three larger codes are excluded from the seed entirely" — and the
  required proof count is 135, not 138. Followed the task; flagged the contradiction rather
  than silently overriding either source. Dropped: 133/139/135 (مبرمج/ممرض/موظف حكومة keep
  86/43/9). Arabic/English reproduced exactly as supplied, including the awkward English
  translations; only incidental leading/trailing ASCII whitespace on a few source rows was
  trimmed.
- **V0015 branch** — 25 rows from `docs/reference/branches.md`, `item_code` = branch number
  ('2'..'26'), no English label supplied.
- **V0016 admin_division** — `is_hierarchical = true`. 1 country row (`item_code='SD'`,
  matching the literal already used in V0006's `sudan_uses_codes` CHECK) + 15 state rows
  (`parent_code='SD'`) + 135 locality rows (`item_code=locality_id`, `parent_code=`the
  state's `item_code`). Keyed on `locality_id`, never the Arabic name — confirmed via

- **V0018 education_level** — 7 rows, `item_code` = '1'..'7' matching the values already
  stored in V0006's `education_level smallint` column (a bare range CHECK, no FK).
  `sort_ordinal` = list position 1–7, not Arabic-alphabetical, per customer.md's explicit
  instruction — the one list exempted from the general rule.
- **V0019 rejection_reason** — 7 rows, `item_code` = 'REJ-01'..'REJ-07' (matching V0009's
  literal `'REJ-07'`). **Provenance gap, flagged rather than silently patched**:
