## The scan-block question, settled against source

The product owner recalled the scan block being exposed to mobile. That is **half true**, and the
two halves have different answers:

**Exposed mid-attempt — YES, and now consumed.** BL-033's `SCAN_BLOCKED` (409) with `blockedUntil`
reaches the phone whenever a scan attempt is refused (`IdentityScanController.java:236-244`,
raised from `IdentityScanService.java:245, 293, 704, 1101`). `ScanBlockedView` renders it.

**Exposed on resume — NO.** The only unauthenticated resume endpoint is `POST
/api/v1/account-check`. `AccountCheckResponse` carries exactly `{outcome, continuation, requestId,
blockedUntil}`, and that `blockedUntil` is the **Stage 2 phone lock** — `AccountCheckService.java:229-231`
reads `currentPhoneLockUntil`, and `AccountCheckContinuation.BLOCKED` is set only from it. The
profile's `status`, which would read `blocked_scan`, is computed into a local `profileStatus` and
never put on the wire. `ProfileController` is `operator.web`, authenticated, back-office only.

So a scan-blocked customer who relaunches gets `continuation=PROCEED`, lands back in the journey
with no signal, and discovers the block only on the next tap to scan. **customer.md:1139-1140 is
not implementable for the scan block.** Filed as **BL-051**. Nothing was faked client-side;
`STATE_CONFLICT` is built as a generic re-sync instead.

## Two more source questions settled before designing

**`scan_blocked_until` is nullable under `blocked_scan`.** `V0039__app_scan_retry_budget.sql:20`
declares it with no `NOT NULL`; no migration adds a CHECK tying it to `status` (V0020 is a
transition guard only). BL-049's edge is schema-reachable — carried as a documented contract
exception, not worked around in the UI.

**The controller comment and the MockMvc test do not contradict each other.**
`IdentityScanController.java:214-218` records a *live* Spring Boot 4.1.0 capture
(`{timestamp,status,error,path}`); `IdentityScanControllerTest.java:195-198` records that *MockMvc*
renders an **empty** body for the same exception and says so outright. Two runtimes, both true. The
mapper therefore keys off the **absence of a `code` member** and never parses a bare body — all
three shapes (live body, empty string, null) are tested to reach the same arm.

## Design decisions

**The mapper has five arms, ordered, and the order is the contract.** Connection-class →
unreachable; any 5xx → unreachable; a body carrying a top-level `code` → the eight 409s and
`SCAN_REJECTED`; otherwise by status (400 client error, 404 re-sync, 409 → the shared
`ProfileAlreadyCompleteException`); else rethrow untouched.

The 5xx arm matters more here than anywhere else in the app: `POST /token` answers an unmapped
`500` when Uqudo's own token endpoint is down (`HttpUqudoClient.mintToken` throws
`IllegalStateException`, nothing catches it), and customer.md:661-662 makes that a connectivity
failure **explicitly not counted against the budget**. The connectivity screen says so in words,
because a customer who sees a failure one screen after attempts start costing them something will
otherwise assume they just lost one.

**In-memory JWS retention.** `RetainedScanStore` is a plain object behind a Riverpod `Provider` —
process-scoped so a retry survives navigation, gone on restart. Never written to `session.db` or
any file (product-owner decision; durable retention is deferred with its own retention rule).
Cleared on: accepted scan, `SCAN_REJECTED`, `ARTIFACT_EXPIRED`, `IMAGES_UNAVAILABLE`. Kept on
everything else — most importantly connectivity, which is the whole point.

**Stage 9 always loads through `POST /registry-review/current`**, on forward navigation and on
resume alike. One code path for both, matching `LaunchScreen`'s doctrine that every destination
re-reads its own values. Costs one extra round trip after a successful scan (two plain SELECTs
server-side); accepted.

**Stage 7 diverges from stages 3-6 deliberately.** They discard the offline return value and
advance anyway, correctly, because they are offline-capable. Stage 7 queues the submission but
**stays put**, because Stage 8 opens the SDK and cannot run offline (customer.md Stage 7's
"Exits"). The resume pointer does not move either, so a relaunch returns here rather than to a scan
that cannot start.

**Camera-permission failures spend nothing.** Every other SDK failure (`USER_CANCEL`,
`SESSION_EXPIRED`, `UNEXPECTED_ERROR`, `REQUEST_TIMEOUT`) calls `/cancel`, which is what actually
spends the attempt — customer.md: "a cancel is not free". But
`SESSION_INVALIDATED_CAMERA_{NOT_AVAILABLE,PERMISSION_NOT_GRANTED}` consumed no Uqudo operation,
and charging a three-attempt budget for a Settings toggle would be wrong.

**Legacy resume values.** `'beyondStage6'` now maps to Stage 7. Without that, a device that
completed Stage 6 on the S5-05/S5-06 build lands on the post-Stage-9 placeholder and can never
reach the identity scan at all — the same class of migration the retired `'verified'` value
already documents. `'beyondStage9'` is the new resting state.

**`SDN_ID` is wired but unproven.** The wire carries only `passport`/`national_id`; the
`national_id → DocumentType.SDN_ID` translation exists solely inside `PluginUqudoScanner`, which
labels the path `[UNVERIFIED]` rather than working. No claim is made that it works.

**`attemptsRemaining` was neither used nor invented.** No screen shows a count; no local counter
exists. Asserted by a test that greps the rendered Stage 8 error screens for count-shaped strings,
rather than left to review.

## R-052 — does consuming the codes close it?

**No. It narrows a fourth time and stays open, now with exactly two residuals.**

What the consumption proved: the eight 409 codes plus `SCAN_REJECTED` **did** map cleanly onto the
screens customer.md stages 8/9/13 specify. One code, one screen; no code without a home, no screen
needing a code that does not exist. Two needed judgement and are recorded as such —
`REGISTRY_PENDING` and `REGISTRY_NOT_READY` drive the *same* pause screen (they stay distinct on
the wire because they arise in different halves of the journey, not because the customer should
see two pauses), and an unknown future code degrades to a re-sync rather than a guessed screen.

**One correction to R-052's own text:** it claimed a `STATE_CONFLICT` "raised by `/token` or
`/scan-result`". `/token` cannot raise it at all — `issueToken` throws none of the four mapped
exceptions. Corrected in RISKS.md.

lands on Stage 9, a refusal drops back to the type selection.

**The two residuals.** (i) The uncoded arm: bare 400 / 404 / 409 / unmapped 500 are still handled
by *status*, which is the thing R-052 was raised about. (ii) BL-051, above.

## Revert-restore proof

**One test needed it, and it caught a mistake.** Per the rule, a direct wrong-value assertion needs
no revert — findings 1–4's tests assert concrete values (`landedPath() == '/stage-8'`,
`resumeStage == 'stage8'`, `store.retained` null, a specific string absent) that cannot pass
against the broken code. The JWS-persistence guard is different: it asserts an **absence**, and a
green suite could otherwise coexist with a broken version, since nothing else would fail if
`keep()` also wrote to drift.

First probe — an `UPDATE … WHERE id = 0` writing the JWS into `DataEntryDraft` — **the test still
passed**, because no draft row exists in that test's setup and the update was a silent no-op. That
is exactly the false confidence the rule exists to prevent. Replaced with an
`insertOnConflictUpdate`:

```
> 00:00 +0 -1: the JWS never reaches durable storage a retained capture leaves no trace of the JWS anywhere in
session.db [E]
>   Expected: false
>     Actual: <true>
    the JWS must never be persisted
```

Probe removed; `grep -c PROBE` → 0; full suite re-run green below.

## iOS — stated plainly, not papered over

**The Uqudo package's iOS support in this repo has only ever been verified by reading its
podspec.** `uqudosdk_flutter` 3.10.0's podspec pins `UqudoSDK 3.10.0` and `OpenSSL-Universal
3.3.3001` exactly at `:ios, '12.0'`, recorded at addition time in the S1-02 report. That is
artifact inspection. **No iOS build has ever happened here** — there is no `ios/Podfile`, no
`Podfile.lock`, no `ios/Pods/`, and `pod install` has never run.

Worse for these screens specifically: `ios/Runner/Info.plist` declares **no
`NSCameraUsageDescription`**, so Stage 8 would terminate the app at first camera access on iOS
today. (`NSPhotoLibraryUsageDescription` is missing too, which `image_picker` needs for Stage 6.)

Pre-existing and out of this task's scope (mobile Dart only, no platform config). Filed as
**BL-052**. Related to but narrower than S1-03: the Info.plist keys need neither AD-003 nor a macOS
machine and could land independently.

**Per-package iOS check owed this session: none.** No new Flutter package was added — `uqudosdk_flutter`
was already pinned, and `intl` was deliberately *not* added (a small local date helper avoids
promoting a transitive dependency to a direct one).
