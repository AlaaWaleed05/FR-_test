## 2. Findings from reading the schema and the closed architecture before writing code

The task asked explicitly to state what the schema decides that the journey doesn't, and to stop
rather than paper over a genuine gap. Five things surfaced during planning, all resolved before
any code was written (full reasoning in the plan file; summarised here):

### 2.1 The schema already forbids plaintext OTP storage — nothing to stop for

`app.otp_challenge` (V0007): `code_hash bytea NOT NULL, -- sha256(salt || code); the code is NEVER
stored`, `salt bytea NOT NULL`. `expires_at` has no DB-computed default beyond a comment
(`issued_at + 5 minutes`), matching customer.md's Policy values exactly — the application computes
it. This is exactly the shape the task wanted; the schema was already correct.

### 2.2 OTP delivery: task text vs. closed architecture — architecture wins

The task says "enqueues one `app.notification_outbox` row per selected channel" for the OTP. The
closed AD-002c design (`docs/components/messaging.md`; `OutboundMessage`'s own `Urgency` Javadoc;
`OutboxDispatcher`'s own class Javadoc: "the outbox exists only for deferred, dispatcher-driven
sends — an INTERACTIVE OTP is sent inline by the OTP service, never enqueued here") says the
opposite: OTPs are `Urgency.INTERACTIVE` and must be sent synchronously, because the outbox is
drained only by a scheduler that does not exist yet (out of scope here and at S3-05). Enqueuing an
OTP into the outbox in this state of the codebase would mean **no real customer would ever receive
their code**, contradicting the entire reason `Urgency` exists as a value.

Escalated to the user via `AskUserQuestion` before writing any code. Decision: **send inline, no
outbox usage in Stage 1b.** The report was asked to record this explicitly — done here, in
`ContactChannelsService`'s own class Javadoc, and in `docs/components/messaging.md`. The
consequence for step 5's proof text ("show three outbox rows") is that the equivalent evidence is
three `notification_dispatched` audit events on the profile's own chain instead — proven in §6.

### 2.3 `fru_app` cannot create the audit chain a new profile needs

`AuditEventWriter`'s only prior caller (`AccountCheckService`, S3-01) and `OutboxDispatcher`'s own
integration test (S3-05) both depend on a `profile`-kind audit chain existing — but no application
code has ever created one, because `fru_app` holds `SELECT` only on `audit.audit_chain` (V0004:
"chain creation is a schema-shaped act"). Every existing chain was pre-seeded by a migration
because its subject was fixed and known ahead of time (`system`/`account_check`, V0034). A
profile's `chain_id` cannot be pre-seeded this way — the `profile_id` doesn't exist until this
endpoint creates it. S3-05's own integration test sidestepped this by building the chain by hand
as `fru_migrator`, explicitly noting "no application code creates profiles yet." S3-06 is that
application code, so this had to be solved for real.

**Fix:** migration `V0036__audit_profile_chain_creation.sql` adds `audit.ensure_profile_chain(uuid)`
— a `SECURITY DEFINER` function (same pattern as `audit.chain_append()`, V0003, which already
exists for the identical reason), idempotent via `ON CONFLICT (chain_kind, subject_id) DO
NOTHING`, with `EXECUTE` granted to `fru_app` only. This keeps chain creation schema-mediated
rather than widening `fru_app`'s table-level grant.

### 2.4 `AuditEventWriter.append` had no way to return the new event's id

`app.profile_status_history.audit_event_id` is a `NOT NULL` foreign key onto
`audit.audit_event.audit_event_id`. The caller creating a profile's first status-history row needs
that id — but `append` returned `void`, because neither prior caller (`AccountCheckService`,
`OutboxDispatcher`) needed it. **Fix:** widened `append` to return `long`. Additive: both existing
callers already discarded the return value.

### 2.5 The wire contract needs `branch`/`accountNumber` even though customer.md's Stage 1b field
list doesn't mention them

Stage 1a and Stage 1b are separate calls with no session token between them (no such mechanism
exists in this codebase, and BL-006's other half — which might introduce one — is explicitly out of
scope). `app.profile` requires `branch_code`/`account_number` (`UNIQUE` together — "one profile per
account"). **Decision:** the 1b request also carries `branch` and `accountNumber`, mirroring
`AccountCheckRequest`'s two fields exactly. A wire-contract necessity, not a new journey field.

### 2.6 Email inclusion and channel enablement — design points the task asked to be stated

- **Email:** presence of a non-blank `emailAddress` means the channel is offered; its absence
  means no `app.profile_channel` row at all (not even `declined`) — proven in §6.
- **A channel disabled by `fru.messaging.<channel>.enabled=false`** is treated exactly like a
  deselected one: recorded `declined`, no challenge, no send. The at-least-one-phone-channel rule
  is evaluated against the *effective* (selected ∧ enabled) set. This says nothing about how the
  app should *advertise* availability up front (R-042, correctly untouched) — only what the
  backend does with a selection it cannot honour. Per the second reviewer pass, the `session_created`
  audit payload additionally records the customer's *raw* selection separately from the *effective*
  one (`smsSelected`/`smsChallenged`, etc.), so "the customer deselected it" and "the customer
  selected it and this deployment couldn't serve it" stay distinguishable in the permanent record
  even though `app.profile_channel` itself has no fourth state for it.

## 3. What was built

### 3.1 Migration `V0036__audit_profile_chain_creation.sql`

```sql
SET LOCAL fru.migration_in_progress = 'on';

CREATE FUNCTION audit.ensure_profile_chain(p_profile_id uuid) RETURNS void
LANGUAGE plpgsql SECURITY DEFINER SET search_path = audit, pg_catalog AS $$
BEGIN
  INSERT INTO audit.audit_chain (chain_kind, subject_id, head_hash)
  VALUES ('profile', p_profile_id::text, NULL)
  ON CONFLICT (chain_kind, subject_id) DO NOTHING;
END
$$;

REVOKE EXECUTE ON FUNCTION audit.ensure_profile_chain(uuid) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION audit.ensure_profile_chain(uuid) TO fru_app;
```

The `REVOKE ... FROM PUBLIC` line was added after the first reviewer pass — see §7.

### 3.2 `AuditEventWriter`/`JdbcAuditEventWriter`

`append(AuditEvent): void` → `append(AuditEvent): long`. The INSERT now ends `RETURNING
audit_event_id`, read back via `jdbcTemplate.query(sql, args, argTypes, RowMapper)` — the
**argument order matters**: `JdbcTemplate` has a `query(String, Object[], int[], RowMapper<T>)`
overload distinct from the variadic `query(String, RowMapper<T>, Object...)`; getting the order
wrong routes silently into the variadic overload with wrong bindings rather than failing to
compile. Verified against the actual `spring-jdbc-7.0.8` bytecode by both reviewer passes.

### 3.3 `sd.gov.bank.fruserupdate.profile` (shared, parallel to `audit`/`corebanking`)

- `domain.ChannelState` — `verified`/`declined`/`unverified`, matching `app.profile_channel.state`'s
  `CHECK` exactly.
- `domain.ProfileRepository` — the port: `ensureAuditChain`, `insertProfile` (profile row + its
  first status-history row together, since the deferred `profile_status_requires_history`
  constraint trigger checks both landed in the same transaction), `insertContactDetails`,
  `insertChannel`, `insertOtpChallenge`.
- `jdbc.JdbcProfileRepository` — the one class that knows these tables' shapes.

### 3.4 `sd.gov.bank.fruserupdate.contactchannels` (the feature)

- `domain.ChannelSelection` — resolves customer selection + enablement into per-channel
  `ChannelDecision`s; throws `NoPhoneChannelSelectedException` if no phone channel survives.
- `domain.OtpCodeGenerator` — `SecureRandom`-based 6-digit code, 16-byte salt,
  `sha256(salt||code)` (matching V0007's own comment). The generated code lives only inside the
  loop iteration that renders it into a message; nothing else in the class carries it.
- `domain.OtpMessageRenderer` — renders the SMS/email bodies (bank name, own channel name, code,
  5-minute validity — the exact shape `StubMessageSenderTest`/`Ucs2SegmenterTest` already proved
  at S3-05) and the WhatsApp `AUTHENTICATION` template payload.
- `domain.DestinationMasker` — `"•••• 4821"` / `"a•••@gmail.com"`, matching customer.md Stage 2's
  row shape, for the response only (never for what's audited or stored).
- `service.ContactChannelsService` — the orchestration (see §2.2 for the inline-send decision).
  Sends happen **before** the database transaction opens (mirroring `OutboxDispatcher`'s own
  reasoning: unbounded external I/O must not hold a transaction open); everything else — chain
  creation, the `session_created` audit event, the profile + history row, every channel row, every
  challenge row, and each `otp_issued`/`notification_dispatched` audit event — happens in one
  transaction. A `MessageSender.send` that throws is caught and recorded as a `PERMANENT_FAILURE`
  result rather than aborting the whole request (added at the first reviewer pass — see §7); only
  the exception's class name is recorded, never `getMessage()` (added at the second reviewer pass,
  to keep a future adapter's exception text — which could quote the OTP-bearing request — out of
  the permanent audit trail).
- `web.ContactChannelsController`/`ContactChannelsRequest`/`ContactChannelsResponse`/`ChannelInfo`
  — `POST /api/v1/contact-channels`, validation mirroring `AccountCheckController`'s `clean()`
  (trim, control-character rejection, length cap).
- `config.ClockConfiguration` — a single injectable `Clock` bean (`Clock.systemUTC()`), needed so
  `ContactChannelsService` never calls `Instant.now()` directly (CLAUDE.md's business-logic
  testability rule: no real clock).
