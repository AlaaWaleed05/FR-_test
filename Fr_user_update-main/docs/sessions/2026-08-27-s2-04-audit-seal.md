## 2. Design decisions, with reasoning

### 2.1 What the seal contains

`audit.audit_seal` already existed from S2-01/V0002 as an **aggregate** row per seal run:
`sealed_at`, `chain_count`, `seal_hash` (sha256 over every chain's `(chain_id, head_seq,
head_hash)`, ordered by `chain_id`), `prev_seal_hash`, `exported_at`, `export_note`. That
table alone cannot verify one specific chain against a seal — there is no per-chain
breakdown to compare against, only one combined hash over every chain at once. **New table
`audit.audit_seal_chain`** (V0031) closes that gap: one row per `(seal_id, chain_id)`
recording `head_seq`, `head_hash` — exactly what AD-005 §5 Layer 4 asks the seal to record
per chain — plus `row_count`, an independently-scanned `COUNT(*)` (not copied from
`head_seq`) as a second, redundant signal. This is additive; the already-migrated V0002
schema was not touched.

### 2.2 How it is produced

**A SQL function, `audit.seal_create()`, invoked externally — no scheduler is built.** The
task's OUT OF SCOPE list excludes "a scheduler," and CLAUDE.md/PROJECT_PLAN.md confirm the
backend has no service layer and no scheduled-job infrastructure today. A SQL function
requires zero application code and is provable with `psql` today, exactly like
`chain_append()`/`verify_chain()` already are. **Operational requirement, not met by
anything in this repository: something outside this codebase (cron, Windows Task Scheduler,
a future backend scheduler) must invoke `SELECT audit.seal_create();` periodically.** This
mirrors the precedent already set for Layer 3 (`db/post-migrate/`): a documented,
externally-invoked SQL step, not a Flyway migration and not application code.

### 2.3 What "exported" means

The `audit_seal` row is the record; the export is a copy of it leaving this database.
`audit.seal_render(p_seal_id)` returns a stable, canonical text rendering of one seal
suitable for `psql -t -A -c "SELECT audit.seal_render(N)" > seal_0000000N.txt`.
`audit.seal_mark_exported(p_seal_id, p_note)` records that the copy happened — a narrow,
one-time, column-limited update. **Stated explicitly, in `docs/components/persistence.md`:
a seal that is created but never copied out of this database provides no protection against
the threat it exists for** — it is just another row a rewriter who already controls the
database controls too. The actual export destination (WORM bucket, printed register,
email, etc.) is **not chosen** — OUT OF SCOPE per the task, which asks for the requirement
to be stated, not an uploader built.

### 2.4 Who may write it, and the seal's own tamper-resistance

**A new role, `fru_sealer`** (V0030), distinct from `fru_app` and `fru_migrator` — the same
separation-of-duties reasoning AD-005 §5 Layer 1 applies to the chain itself: if the role
that writes audit events could also reseal the chain, a single compromised `fru_app`
credential could tamper the trail and cover its tracks by producing a new seal over the
tampered state. `fru_sealer` gets `USAGE` on schema `audit`; `SELECT` on `audit_chain`,
`audit_event`, `audit_artifact`, `audit_seal`, `audit_seal_chain`; `INSERT` on the two seal
tables; and a column-limited `UPDATE (exported_at, export_note)` on `audit_seal` only.
`fru_app` gains nothing — confirmed live (§4.6).

**The seal itself must be append-only, or it becomes the weak link.** New Layer-2-style
triggers (V0032/V0033), mirroring the existing `reject_mutation()`/`artifact_guard()`
pattern: `audit_seal_chain` is fully insert-only; `audit_seal` allows exactly one narrow
update per row — a one-time `NULL → value` set of `exported_at`/`export_note`
(`audit.seal_guard()`, structurally identical to `artifact_guard()`'s "the only permitted
update is X" shape). Both tables sit inside schema `audit`, so Layer 3 already covers them
by schema name with no changes needed there — modulo the deployment-ordering fix in §7.1.

## 3. Verification function

**`audit.seal_verify(p_seal_id)`**, one row per chain the seal covers: `chain_id`, `status`
(`matches` / `grew_consistently` / `diverged`), `sealed_head_seq`, `sealed_head_hash`,
`current_row_count`, `reason`.

**Critical design point.** The existing `audit.verify_chain()` (V0003) recomputes hashes
from raw row content but compares the *final* result only against `audit.audit_chain.
head_hash` — a plain, mutable column with no immutability trigger of its own. A rewriter
who tampers a row can also directly `UPDATE audit.audit_chain SET head_hash = ...` to match
a freshly recomputed chain, and `verify_chain()` will then report `ok = true`. `seal_verify()`
therefore recomputes the hash chain **independently from row content alone** — the same
canonicalization `chain_append()`/`verify_chain()` use — walking `audit_event` from
`seq = 1` to the **sealed** `head_seq`, and compares the result **only** against
`audit_seal_chain.head_hash`, a value in a table that is itself immutable and expected to
have left the database. It never reads `audit_event.content_hash`/`row_hash` or
`audit_chain.head_hash` as ground truth.

`current_row_count` is deliberately a `COUNT(*)`, not `audit_chain.head_seq` or a
`MAX(seq)` — named for exactly what it is, since a rewriter could also have overwritten
`head_seq`. It is not a full re-verification of the region beyond the sealed prefix (that
remains `verify_chain()`'s job for the live chain); `seal_verify()`'s job is the sealed
prefix, plus reporting whether the chain grew beyond it.

**`audit.seal_verify_history()`** (added during the review pass, see §7.5) complements this
by checking the seals themselves: recomputes each seal's `seal_hash` from its own
`audit_seal_chain` rows and confirms `prev_seal_hash` correctly chains to the prior seal
(recomputed, not stored — see the code comment on why), or the genesis constant for the
first.

Implemented via a shared helper, `audit.seal_verify_prefix(p_chain, p_upto_seq)`, that does
the walk-and-recompute once. `audit.verify_chain()` (V0003) was left untouched.

### 7.1 BLOCKER — V0031/V0032 cannot be applied to any correctly-deployed database

V0003's own comment already stated the contract: a migration issuing DDL in schema `audit`
must `SET LOCAL fru.migration_in_progress = 'on';` first, because Layer 3 blocks unguarded
DDL there. V0031-V0033 are the first migrations after S2-01 to do so, and none of them set
the flag. It only worked on a virgin database where every migration ran before the
post-migrate script — the exact opposite of every real deployment past S2-01, and a case
Testcontainers-based tests can never exercise (they never run `db/post-migrate/`).
**Fixed:** added `SET LOCAL fru.migration_in_progress = 'on';` as the first statement of
V0031, V0032 and V0033. Re-verified live in §4.0 by installing Layer 3 *before* running
V0030-V0033, the realistic ordering.

### 7.2 BLOCKER — `fru_sealer` had no `SELECT` on `audit.audit_artifact`

`seal_verify_prefix()` reads `audit_artifact.sha256` for every artifact-linked event, and is
SECURITY INVOKER. The V0033 grant list omitted `audit_artifact`, so `seal_verify()` failed
with `permission denied for table audit_artifact` for `fru_sealer` itself on any chain
containing an artifact-linked event — in practice, every real profile chain. **Fixed:**
added `audit.audit_artifact` to the `GRANT SELECT` list in V0033. Re-verified live in §4.2 —
`seal_verify()` now succeeds as `fru_sealer`.

### 7.3 SHOULD FIX — `seal_create()`'s three snapshots could disagree

`chain_count`, the `seal_hash` loop, and the `audit_seal_chain` insert were three separate
SQL statements; under READ COMMITTED each takes its own snapshot, so a `chain_append()`
landing between them could produce a seal whose aggregate hash does not match its own
per-chain rows — permanently, since both tables are append-only. **Fixed:** capture
everything in one `INSERT ... SELECT` into a temp table first, and derive `chain_count`,
`seal_hash` and the `audit_seal_chain` rows from that single, atomic read.

### 7.4 SHOULD FIX — concurrent `seal_create()` could fork the seal-of-seals chain

Reading `prev_seal_hash` took no lock; two overlapping invocations could both read the same
predecessor and both insert. **Fixed:** `pg_advisory_xact_lock(hashtext('audit.seal_create'))`
at the top of `seal_create()`, serializing callers for the duration of the transaction — the
same role `chain_append()`'s `SELECT ... FOR UPDATE` plays per chain.

### 7.5 NOTE — nothing verified `seal_hash`/`prev_seal_hash` themselves

`seal_verify()` only ever read `audit_seal_chain.head_hash`; no function recomputed
`audit_seal.seal_hash` or walked `prev_seal_hash`, so a mismatch from 7.3/7.4 (or direct
tampering) was undetectable in-database. **Fixed:** added `audit.seal_verify_history()` —
see §3 and §4.7 for the live proof.

### 7.6 NOTE — `seal_verify()`'s `current_head_seq` was really a row count

Named to imply a verified sequence position, but computed as `COUNT(*)`, which only
coincides with a true `head_seq` while the region beyond the sealed prefix is itself
gapless — not exploitable (already caught by `seal_verify_prefix`'s own gap check inside the
sealed range), but misleading to an operator reading the output. **Fixed:** renamed to
`current_row_count` throughout, with a code comment explaining exactly what it is and is
not.

### 7.7 NOTE — six files cited a session report that did not exist yet

Correct at the time of the review (this file). No action needed once this report lands, as
it now does.

### 7.8 NOTE — `.claude/settings.json` change is unrelated to S2-04

Confirmed: this is the harness-generated entry from S2-10, expected per this task's own
step 0 instruction, and left alone as instructed.

### 7.9 Verified correct, no finding

The core design property (never trusting stored hash columns or `audit_chain.head_hash`),
PL/pgSQL variable/column-name safety in `seal_verify()`, immutability against the table
owner, the zero grant for `fru_app`, Flyway placeholder wiring across all three invocation
paths, the `pg_class`/`pg_namespace` fix in the integration test, and the absence of any SQL
injection surface were all checked and hold, several with live re-verification by the
reviewer against a real PostgreSQL 18 instance.

## 8. What failed, summarized

- The first pass at V0031/V0032 did not account for Layer 3 already being active in any
  real deployment — found only because the reviewer re-tested against that realistic
  ordering rather than trusting the original from-scratch run, which had accidentally
  masked the bug (§7.1).
- `fru_sealer`'s grant list was missing `audit_artifact`, breaking verification for the role
  meant to use it (§7.2).
- `seal_create()`'s original three-statement snapshot and unlocked `prev_seal_hash` read were
  both real, if narrow, race conditions (§7.3, §7.4) — neither was exercised by any proof
  run single-threaded, and both would have shipped invisibly without the reviewer's static
  read of the code.
- One integration-test authoring mistake (`information_schema.tables` silently filtered by
  the querying role's own zero-grant design) was self-diagnosing and fixed immediately
  (§6.2).

Everything in §4, §5 and §6 reflects the final, fixed state, re-verified from a database
reset from scratch after every fix above.
