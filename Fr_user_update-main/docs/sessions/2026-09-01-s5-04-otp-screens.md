## 2. Screens built

- **`ChannelVerificationScreen`** (new, `/channel-verification`) — one row per selected
  (non-declined) channel: icon/name, masked destination, its own 6-digit code field
  (`ArabicDigitInputFormatter` + `digitsOnly`, forced LTR — the fifth "LTR island"), its own resend
  control, its own always-visible state line. Next enables the moment any phone row (`sms`/
  `whatsapp`) verifies; tapping it with an unverified selected channel shows the first
  `AlertDialog` in this codebase (no existing convention — confirmed by grep), "go back and verify"
  listed first so it renders at the reading-first side under the app's forced RTL
  `Directionality`; no dialog when everything is verified.
- **`SessionPendingScreen`** — repurposed, not deleted: was S5-02's "Stage 2 doesn't exist yet"
  placeholder reached after Stage 1b; now reached after Stage 2 completes, filtering to `verified`
  channels and reworded copy ("باقي خطوات التحديث ستتوفر في إصدار لاحق"). Self-loading pattern and
  abandon action unchanged.
- **`channel_labels.dart`** (new, small) — `channelLabel()` extracted from `SessionPendingScreen`'s
  private switch, now shared by both screens.
- **No schema migration.** `LocalProgress.resumeStage` already holds free text; a third value
  (`'verified'`) needs no new column, no `schemaVersion` bump.
- **Write-through cache, not new state**: `EntryRepository.verifyChannel`/`resendChannel` extend
  the existing S5-02 `channelsSummary` "display-only cache" — a `VERIFIED`/`ALREADY_VERIFIED`
  outcome rewrites that channel's cached entry, inside a `_db.transaction()` (added under review,
  see §3). Locked/countdown state is deliberately **not** persisted — disclosed on the screen's own
  doc comment as a resume-time staleness gap, self-correcting on the next attempt.
- **Resend countdown is never client-computed.** `OtpResendResponse.secondsUntilAllowed` is the
  only source (`-1`→`null` at the API boundary); the button stays tappable and only shows a
  countdown once told a real one via `TOO_SOON` — CLAUDE.md forbids re-enforcing policy values
  client-side. Disclosed on the screen's doc comment that this means no proactive 30s lock on a
  fresh `ISSUED`.
- New `EntryApi.verifyChannel`/`resendChannel` + `DioEntryApi` implementations. Backend outcome
  strings are Java enum names (`WRONG_CODE`, not `wrongCode`) — decoded via explicit `switch`es,
  not the `.byName(.toLowerCase())` pattern the rest of the file uses for single-word enums.

## 3. Review — two passes, both found real defects

**First pass**: 3 SHOULD-FIX + 4 NOTE, all fixed same session.

- Lost-update race in the `channelsSummary` write-through cache: two rows verifying concurrently
  (the screen's submit guard is per-row) could clobber each other's state via an unsynchronised
  read-modify-write. Fixed with `_db.transaction()`; regression test added and **revert-tested**
  (temporarily un-wrapped + an injected yield point, confirmed the test fails; restored, confirmed
  it passes) per CLAUDE.md's indirect-assertion discipline.
- No test proved "email alone never enables Next" — added.
- Dual-form Arabic verbs (`منهما`/`تُحفظا`) in the status line, singular-form in the dialog title,
  were only grammatically correct for specific channel counts and wrong the moment a third selected
  channel made the unverified list one or three items. Reworded to invariant phrasing (`باقي
  القنوات`, `لن يتم حفظ`), matching `ContactChannelsScreen._consequenceText`'s existing precedent.
- Plus: a bare `profileId!` null-assertion (named `StateError` instead of an unrelated `TypeError`);
  a resend-only path to both-phone-locked left no navigation to `/terminal` (`/otp/resend` carries
  no block timestamp — closed by checking `_allPhoneRowsLocked` after any `CHANNEL_LOCKED` resend
  outcome too); `.inMinutes` truncation understated the remaining block by up to a minute (ceiling
  division); `PGPASSWORD` was an argv element in the live-proof script's `docker exec` call,
  visible in the host process table — moved to the child process's environment (`docker exec -e
  PGPASSWORD` with no `=value`, forwarding the caller's own env, verified against the real
  container).

**Second pass, against the fixed diff, found real gaps in the first pass's own fixes** — this
project's now-familiar pattern:

- The deferred Stage 0 `blocked` gap had no BACKLOG.md entry despite this row's own title naming
  it — closed with BL-021 (§1 above).
- The SAME Arabic-invariance bug survived in the terminal block message: `'$minutesLeft دقيقة'` is
  wrong for 3–10 (needs the plural `دقائق`) and reachable — `OtpVerificationService.finish` reports
  the *remaining* lock time on every verify attempt made while blocked, not just when the lock is
  first set, so a relaunch mid-block can surface any count 1–60. Closed with an Arabic
  numeral-agreement helper (1 → `دقيقة واحدة`, 2 → `دقيقتان`, 3–10 → plural, 11+ → singular);
  regression tests added for the 15-minute and 3-minute cases.
- The resend-lock fix's own comment and test name mischaracterised the scenario as "a customer who
  only taps resend locks a channel" — `OtpVerificationService.reserveResend` only ever returns
  `CHANNEL_LOCKED` when the channel was *already* locked by an earlier wrong-code verify sequence;
  resend never causes one. The reachable case is the disclosed resume-staleness gap (a lock learned
  via resend after it was lost from the local cache). Comment and test renamed to describe it
  accurately; the guard itself was already correct.
- A masculine/feminine mismatch: the per-row state line ("موثق"/"حفظه", masculine) disagreed with
  the locked message directly below it ("هذه القناة", feminine — القناة is feminine). Fixed to
  "موثقة"/"حفظها".
- A tatweel-connector artifact: `'بـ$verifiedNames'` rendered as `بـالرسائل النصية` for any name
  starting with the definite article, where standard orthography merges to `بالرسائل`. Fixed by
  attaching `ب` directly.
- The dialog title's plural noun (`القنوات التالية`, "the following channels") was wrong for
  exactly one unverified channel — reworded to avoid the countable noun entirely (`لم يتم التحقق
  من: ...`), matching the status line's own earlier fix.

Regression test added for every fix in both passes. Asked explicitly whether any proof output or
log line can contain an OTP code: confirmed clean both passes — `nextWrongCode()`'s return value in
the live-proof script flows only into the API call, never into a `stdout`/`stderr` line; no
`print`/`log`/`LogInterceptor` exists anywhere reachable from this diff.

## 4. Proof

extended past Stage 1a/1b into Stage 2 — every outcome obtainable without a real OTP code (see §5):

```

sms attempt 1: channel=sms outcome=wrongCode state=unverified sessionBlockedUntil=null
whatsapp attempt 1: channel=whatsapp outcome=wrongCode state=unverified sessionBlockedUntil=null

Exhausting sms's 5-attempt budget:

sms attempt 6: channel=sms outcome=channelLocked state=unverified sessionBlockedUntil=null

whatsapp attempt 5: channel=whatsapp outcome=wrongCode state=unverified sessionBlockedUntil=2026-09-01 20:54:24.536860Z
Both phone channels locked — sessionBlockedUntil=... (mobile screen navigates to /terminal on this signal)

Resend TOO_SOON (immediate second resend on email):
  1st resend: outcome=tooSoon
  2nd resend (immediate): outcome=tooSoon secondsUntilAllowed=30

Resend cap (3/channel/session) via backdated issued_at:
  real resend 1: outcome=issued
  real resend 2: outcome=issued
  real resend 3: outcome=issued
  real resend 4: outcome=capExhausted
```

No OTP code, real or synthetic, appears in any printed line (redaction discipline, see §3). The
resend-cap backdating used `docker exec ... UPDATE app.otp_challenge SET issued_at = ...` — the
same technique `OtpVerificationIntegrationTest.backdateMostRecentIssuedAt` uses at the SQL level,
selecting by `MAX(expires_at)` not `MAX(issued_at)` for the same reason that test documents. A
direct `psql` query confirmed no `audit.audit_event` payload for any `otp_*` event type carries a
`"code"` field, across 10 sampled rows from this session's own run.

**`VERIFIED` is not live-provable from outside the backend JVM** — `StubMessageSender`
(`backend/.../messaging/stub/StubMessageSender.java:41-47`) deliberately never retains a sent
message's rendered body (the OTP code) anywhere reachable outside the same process; only a salted
hash reaches `app.otp_challenge`, confirmed by `OtpVerificationIntegrationTest`'s own doc comment.
This is architectural, not a gap in this session's effort. `VERIFIED`/Next-enabling/the dialog/
navigation are proven instead via `entry_repository_test.dart`/`channel_verification_screen_test.dart`
against `FakeEntryApi` — the correct proof form under CLAUDE.md's live-vs-test rule, since
`OtpVerificationIntegrationTest` already independently proves the server-side `VERIFIED` path live.

Both phone channels locked → sessionBlockedUntil observed non-null live (above); the screen's
reaction to it (navigate to `/terminal`, no `_db.clear()`) is a direct widget assertion — a broken
guard could not pass it, so no further live capture was needed for that half.

Confirmation dialog: exactly one shown with an unverified selected channel, "go back" listed first;
none shown when every selected channel is verified — both direct widget assertions
