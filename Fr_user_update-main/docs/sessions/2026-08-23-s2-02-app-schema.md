## 3. The plan, and what changed after approval

Full plan: `C:\Users\DELL\.claude\plans\lovely-strolling-nautilus.md`. Approved without
requested changes. Two judgment calls the plan flagged in advance, both followed through as
planned:

1. **Two FK constraints deferred to S2-03.** `profile_customer_data.occupation_fk` (composite
   FK to `ref.reference_item` via the `occupation_list` generated column) and
   `profile_status_history`'s FK to `ref.reference_item` for the rejection-reason code cannot
   be created — `ref.reference_item` does not exist yet (OUT OF SCOPE, S2-03). Every column is
   kept exactly as the AD-005 report specifies; only the two FK constraints are omitted, with a
   comment at each site giving the exact `ALTER TABLE ... ADD CONSTRAINT` S2-03 should run.
2. **Grants and the insert-only trigger for `app` are an extension beyond the report's elided
   text**, following the same role-separation principle §5 establishes for `audit`. For
   `profile_status_history`'s insert-only enforcement, a new `app.reject_history_mutation()`
   function was written instead of reusing `audit.reject_mutation()` verbatim, because that
   function hardcodes the literal string `'audit.'` in its error message and would misreport
   the schema if applied to an `app` table.

**Two things surfaced during implementation that the plan did not anticipate** (both found by
actually running the new connectivity test, not from documentation):

- **`org.flywaydb:flyway-core` + `flyway-database-postgresql` alone do not activate Spring
  Boot's `FlywayAutoConfiguration`** on this Spring Boot version (4.1.0). Boot 4.1 split
  autoconfiguration into per-feature modules; Flyway's now lives in a separate
  `org.springframework.boot:spring-boot-flyway` artifact that has to be added explicitly. Found
  live: the connectivity test's `Flyway` bean autowired as `null` until this dependency was
  added. See §5 below.
- **`spring.flyway.placeholders.fru_app_password=...` (dot notation) silently fails** to
  resolve the `${fru_app_password}` SQL placeholder, because Spring's relaxed binding for a
  `Map<String,String>` property strips underscores from dot-separated key segments. The fix is
  bracket notation: `spring.flyway.placeholders[fru_app_password]=...`. This was a **live bug
  in `application.properties`** since S2-01 — invisible until now because every prior
  `flyway:migrate` run used the Maven plugin's own XML `<placeholders>` config (a completely
  separate mechanism from Spring's property binding), never Spring Boot's actual
  `FlywayAutoConfiguration`. Fixed in `application.properties` as well as the test, with a
  comment explaining why.
- **`spring-boot-flyway` was initially added at main (compile) scope.** Caught by the
  `@agent-reviewer` review (§10): this would have silently changed the *deployed* application's
  boot behaviour — it would run Flyway `migrate()` as `fru_migrator` (owner of everything) on
  every startup, instead of the intended model where the running app connects only as
  `fru_app` with zero DDL rights and migrations are applied separately via the
  `flyway-maven-plugin`. Moved to `<scope>test</scope>` — sufficient for the integration test
  (test-scope dependencies are on the test classpath), and confirmed with a full
  `./mvnw package -DskipTests` rebuild afterwards that production packaging is unaffected.
- **A stale, incorrect exclusion in `BackendApplicationTests`.** Its
  `spring.autoconfigure.exclude` listed the pre-Spring-Boot-4.0 fully-qualified names
  (`org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration` /
  `...autoconfigure.flyway.FlywayAutoConfiguration`), neither of which exists anywhere on this
  classpath (confirmed by scanning every jar). This had been silently harmless throughout S2-01
  purely because nothing on the classpath forced `DataSourceAutoConfiguration`'s bean method to
  actually run — until adding `spring-boot-flyway` changed that, and `./mvnw test` broke with a
  real `HikariDataSource` bean-creation failure. Fixed by correcting the exclusion to the real,
  current FQCNs (`org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration` /
  `org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration`), confirmed against
  the actual `.class` files inside `spring-boot-jdbc-4.1.0.jar`. Re-verified Docker-independent
  afterwards.

### 7b. Status transitions — no schema-level constraint exists

The AD-005 report's schema has **no generic transition constraint** on `app.profile.status`:
only FK membership in `app.status_code`, plus the specific approve/reject statements' own
`WHERE` predicates. Demonstrated rather than invented:

```
=== setup: a fresh profile, status = in_progress ===
INSERT 0 1
=== attempt an ILLEGAL jump: in_progress -> approved, skipping submitted entirely ===
=== (a raw UPDATE, not the report's guarded approve statement) ===
UPDATE 1
=== result: did it succeed? ===
              profile_id              |  status
--------------------------------------+----------
 ea9764f0-d687-471f-b8f3-130e3ae57f05 | approved
(1 row)
```
The raw UPDATE succeeded. **Conclusion, stated plainly per the task's instruction:** the
schema does not constrain arbitrary status transitions generically. Legal-prior-state
enforcement exists only in the specific approve/reject statements' own `WHERE` clauses (see
§7c and the V0009 comment), not as a table-wide guard. No constraint was invented to paper
over this.

## 8. The connectivity integration test

**Choice: Testcontainers**, using the exact same `postgres:18` image and the exact same
`db/init/01-create-migrator.sh` init script docker-compose.yml mounts (copied into the
container via `withCopyToContainer`), so there is one source of truth for how `fru_migrator`
gets created. This matches the AD-005 report §11's own stated gate design.

`AppSchemaConnectivityIntegrationTest`, tagged `@Tag("integration")`:
- Boots the **full** Spring context — unlike `BackendApplicationTests`, does **not** exclude
  `DataSourceAutoConfiguration`/`FlywayAutoConfiguration`.
- Wires `spring.datasource.*` (as `fru_app`) and `spring.flyway.*` (as `fru_migrator`, with the
  `fru_app_password` placeholder — using the bracket-notation fix from §3) to the container via
  `@DynamicPropertySource`.
- Asserts, via an autowired `JdbcTemplate`, that the `app` and `audit` schemas and
  representative tables (`app.profile`, `audit.audit_event`) exist, and that
  `app.status_code` has all 9 seeded rows.

Gating: excluded from `./mvnw test`/`./mvnw verify` by default via a new
`excluded.test.groups=integration` Surefire property; a new `db-integration-test` Maven profile
clears it. Documented in CLAUDE.md: `./mvnw test -Pdb-integration-test` (requires Docker
running).
