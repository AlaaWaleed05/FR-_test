## 2. R-044 — resolved before any schema work

**Decision: the per-channel counters (`wrong_code_attempts`, `resend_count`, `locked_at` on
`app.profile_channel`) are genuinely per-session and reset on re-entry.** This confirms — does not
change — what S3-07's `upsertChannel` already does.

**Reasoning:** customer.md scopes both counters explicitly *per session* ("locks... for the
session", "3 per channel **per session**"), and the "Phone number wrong → Back to 1b" correction
reuses the same `profile_id` with no new session concept anywhere in this codebase — S3-07's
re-entry already *is* the fresh-session boundary the spec describes.

**What bounds the abuse, stated precisely:**

- **Wrong-code guessing via repeated re-entry** — bounded by a mechanism this session adds. Stage
  2's own policy value, "Both phone channels locked... terminal... 15 minutes, escalating to 1
  hour on a repeat in the same session," only makes sense as a block on *the next Stage 1b
  re-entry* — a channel that hit its wrong-attempt limit "cannot be retried" (V0007), so the only
  way back into verification is a fresh 1b submission. Two new columns, `app.profile.phone_lock_until`
  and `app.profile.phone_lock_escalated` (V0037), are written by `OtpVerificationService` when
  every selected phone channel locks, and read by `ContactChannelsService`'s re-entry path to
  refuse a re-entry attempted before the lock expires. Unlike the per-channel counters, these two
  columns deliberately **do not** reset on re-entry — resetting them would defeat the only thing
  that makes them a bound at all. `phone_lock_escalated` never resets either: once true, every
  future lock uses the 1-hour duration, the policy value's stated ceiling.
- **Resend-only cycling (never entering a wrong code)** — **nothing bounds this.** A client that
  calls Stage 1b repeatedly and only ever requests resends never trips the wrong-code lock above,
  so the escalating block never engages, and re-entry still resets `resend_count` to 0 every time.
  This is the same gap R-044 originally flagged and BL-007 already covers (now extended to name
  `/api/v1/otp/resend` explicitly — see BACKLOG.md). Stated plainly, not implied to be handled.

RISKS.md's R-044 row updated to ✅ Retired with this reasoning; BACKLOG.md's BL-007 extended to
name the new endpoint.

## 3. What was built

New package `sd.gov.bank.fruserupdate.otpverification` (`domain`/`jdbc`/`service`/`web`), mirroring
`contactchannels`'s shape:

- **`POST /api/v1/otp/verify`** — `OtpVerificationService.verify(profileId, channel, code)`. Loads
  channel state under `SELECT ... FOR UPDATE` (`OtpVerificationRepository.findChannelStateForUpdate`)
  as the transaction's first statement. Already-verified is idempotent (200, no writes). Locked
  channels are rejected as `CHANNEL_LOCKED` without touching the wrong-attempt counter. An
  expired/missing challenge is rejected as `EXPIRED`, also uncounted. A correct code (compared via
  `OtpCodeGenerator.matches`, using `MessageDigest.isEqual`) consumes the challenge and marks the
  channel verified. A wrong code increments `wrong_code_attempts`; hitting 5 locks the channel and,
  for a phone channel only, may trigger the session-wide phone lock (see §2).
- **`POST /api/v1/otp/resend`** — `OtpVerificationService.resend(profileId, channel)`. Two phases:
  Phase 1 (inside a transaction, under the same row lock) validates the already-verified/locked/cap
  states and the 30s/60s/120s escalating delay (`OtpVerificationPolicy.RESEND_DELAYS`, indexed by
  the pre-increment `resend_count` — matches V0007's own `-- 0,1,2 -> 30s/60s/120s unlock` comment
  exactly) against `mostRecentIssuedAt`, and — if eligible — reserves the slot by incrementing
  `resend_count` immediately, before any send. Only then is `MessageSender.send()` called (never
  inside a transaction, matching `ContactChannelsService`'s established shape). Phase 2 (a second,
  short transaction) invalidates the prior challenge, inserts the fresh one, and audits.
- **Migration V0037** — two columns on `app.profile`: `phone_lock_until timestamptz`,
  `phone_lock_escalated boolean NOT NULL DEFAULT false`. No other schema change was needed;
  `app.profile_channel`'s counters and `app.otp_challenge`'s `resend_index`/`expires_at` already
  existed with the right `CHECK` bounds and grants.
- **`ContactChannelsService`** gained `checkPhoneLockNotActive`, called in the re-entry branch
  before anything is generated or sent: if `phone_lock_until` is in the future, audits
  `contact_channels_rejected` (reason `phone_temporarily_blocked`) and throws
  `SessionTemporarilyBlockedException`, mapped by `ContactChannelsController` to HTTP 429.
- **`ProfileRepository`/`JdbcProfileRepository`** gained `currentPhoneLockUntil`,
  `phoneLockEscalated`, `applyPhoneSessionLock`, and (added during review, see §5)
  `lockProfileRow`.
- **Audit events**, all on the profile's own chain: `otp_verification_attempted` (channel, outcome,
  attemptNumber — every attempt, including wrong/expired/locked), `otp_channel_locked` (channel,
  wrongCodeAttempts), `otp_session_locked` (untilIso, escalated), `otp_resend_issued` (channel,
  resendNumber — issuance only, not refusals), plus the reused `notification_dispatched` and
  `contact_channels_rejected`. None ever carries the code or its hash.
